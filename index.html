Image → 3D for Game Studio: a dwarf, four ways

Ryandi · 30 Oct 2026 · Why: Game Studio's 3D node moved off the Tripo CLI (browser login, kept failing on cardinal) to Tripo on Fal. This page checks the new option against the old one.

The input is one dwarf, drawn as four views (front, left, back, right) with Nano Banana on the Game Studio canvas: studio.argus.dev/games/da22ab81-89bb-4876-b496-6f483d5bc5e2/canvas. Every option got the same images and a 20,000-triangle cap. Each ran 3 times; option ④ ran 5 times.

Verdict: use Tripo H3.1 multiview on Fal (②) as the default.
  • It's the only option that gets the back right: the crossed straps and chainmail from the back view. ③ and ④ only see the front, so they guess the back: the beard pokes through, with a plain skirt and no straps.
  • It comes finished (textured, UV-mapped, PBR) for $0.30. The old CLI path (①) also used the 4 views, but it returned a grey shape; colour cost another step and more credits, and it needed someone's Chrome login.
  • P2 front-only (③) costs 3.7× as much with the same invented back. It's worth one more try on a hard-surface subject (a chest, a weapon), where P2's cleaner shapes might matter. Otherwise drop it.
  • All of them import into Unity cleanly, but every model needs three fixes: turn it 90°, set its scale, and compress its textures. Details in Unity.
  • Runs are consistent: the repeat runs of each option look nearly identical.

What we'd need to handle in Unity

  1. Imports are clean. 14 of 14 imported with no warnings or errors, about 0.2 s each.
  2. Our Unity projects can't open a GLB yet. None of them has a glTF importer. Add com.unity.cloud.gltfast, or have Game Studio convert to FBX before it hands the file to Unity. The old CLI's files were also mesh-compressed (meshopt), which needs com.unity.meshopt.decompress. That package only exists as experimental 0.3.0, because glTFast 6.20 refused the 0.1 preview. The Fal models don't need it.
  3. Every model faces sideways (−X). Unity characters face +Z, so each needs a 90° turn on Y. Fix it once on import or in the prefab. Fal's orientation / export_orientation options might fix it at the source; untested.
  4. Every model is exactly 1 unit tall. Tripo normalises the size rather than using real-world size, so each asset needs a deliberate scale (a dwarf ≈ 1.3 m). Fal's auto_size option might help; untested.
  5. Textures are heavy as imported. Each model has three 2048² maps (colour, normal, and occlusion/roughness/metal), imported uncompressed (RGB24/ARGB32): about 56 MB of GPU memory per character. Compressing them (BC7/ASTC) or using 1024² brings that to roughly 4–17 MB. Do this before these go into a game.
  6. Materials use glTFast's own shader (glTF-pbrMetallicRoughness). It looks right under URP, but production assets should be moved to the game's own shaders.
  7. P2 has about 2.4× the vertices of H3.1 at the same triangle count (28,835 vs 12,658). That means more UV seams. It's a small GPU cost and not a blocker.
  8. Nothing is rigged. None of the outputs has a skeleton. Rig and animate in a DCC tool or Mixamo; Fal has no Tripo rigging.

Opinion: in Unity, ② looks closest to the concept from every side, and it's usable in a game after the turn, scale and texture fixes. ③ is just as good from the front, but its back doesn't match the design. ① can't be judged on looks without paying for its texture step, and its shape is softer than ②'s.

How this was run

The Fal runs used Game Studio's own Fal adapter (main @ 584ca3a), the same code the Model node runs. The old runs used the Tripo CLI with the arguments the BB plugin used (generate multiview-to-model --model tripo-p2 --param face_limit=20000, then task get --download). Triangle and vertex counts come from the GLB files. The Unity figures come from a batch import in a throwaway project.
